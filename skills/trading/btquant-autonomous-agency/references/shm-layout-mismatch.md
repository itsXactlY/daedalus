# Python/C++ Shared Memory Layout Mismatch — HotSpine SHM

The BTQuant data pipeline uses a C++ HotSpine consumer reading a Python
producer's shared memory file at `/dev/shm/btquant`. When the Python
producer and the C++ consumer define their struct layouts independently
and don't share a header, layout mismatches cause silent data corruption.

## The pattern

Two separate files define the same data layout:

1. **Python side** — `mock_data_producer.py` uses `struct.pack_into()`
   with hardcoded format strings:
   ```python
   HEADER_SIZE = 4096
   TRADE_SIZE = 40
   OB_SIZE = 6464  # alignas(64): 6424 -> 6464
   OB_HEADER = 24  # uint64+uint64+uint32+uint8+uint8+uint8[2]
   ```

2. **C++ side** — `include/hotspine_data_bridge.hpp` defines matching
   structs with `sizeof()` as the natural stride:
   ```cpp
   struct HotOrderbookSnapshot {
     uint64_t ts_exchange;
     uint64_t ts_local;
     uint32_t symbol_id;
     uint8_t  bids_count;
     uint8_t  asks_count;
     uint8_t  padding[2];
     std::array<HotOrderbookLevel, 200> bids;  // 200*16 = 3200
     std::array<HotOrderbookLevel, 200> asks;  // 200*16 = 3200
   };
   // Natural sizeof = 6424. Python stride = 6464. MISMATCH.
   ```

The C++ consumer iterates the orderbook ring buffer with
`sizeof(HotOrderbookSnapshot)` as the stride. The Python producer writes
at its declared `OB_SIZE = 6464`. After the first orderbook, the two
are out of sync.

## Two documented instances

### Bug #1: HEADER_SIZE mismatch (fixed 2026-06-18, commit 5d5a4e0a)

Python was using `HEADER_SIZE = 80`. C++ was using
`HOTSPINE_HEADER_SIZE = 4096` (cache-line aligned). Trades started at
SHM offset 80 in Python, C++ read at offset 4096. The first ~4016 bytes
were mmap noise interpreted as trades:
```
[WARNING] Invalid trade data - price: 2.121995799e-314, size: 0
```
`price = 2.12e-314` is a denormal float, the classic signature of
uninitialized memory being interpreted as a double.

**Fix:** Python `HEADER_SIZE = 4096`. Now matches C++.

### Bug #2: alignas(64) missing on C++ struct (fixed 2026-06-18, commit 6e0cf798)

Python was padding each orderbook to 6464 bytes (64-byte aligned).
C++ `sizeof(HotOrderbookSnapshot)` was 6424 (natural alignment only).
The C++ consumer iterated the ring buffer at stride 6424 while Python
wrote at stride 6464. After the first orderbook, the C++ was reading
from the middle of the next orderbook's padding.

**Symptom:**
```
[OrderbookPanel] Auto-selected: UNKNOWN (ID=2965605936)
[OrderbookPanel] Rendering. SymID=2965605936 ActiveSyms=218
```
`ID=2965605936` is a garbage value (not in the 1-20 symbol registry),
`ActiveSyms=218` is some internal counter that grew unbounded as the
C++ found more and more "garbage" symbols in misaligned slots.

**Fix:**
```cpp
struct alignas(64) HotOrderbookSnapshot {
  // ... same fields ...
};
// sizeof now rounds up to 6464, matching Python's OB_SIZE.
```

`HotTrade` does NOT need `alignas(64)` — its natural `sizeof(40)`
already matches Python's `TRADE_SIZE=40`.

## Why both bugs existed

Neither the 100-iteration code review nor the openhands smoke test
caught these because:
- The review checked compile-time correctness (struct layouts
  matched within the C++ side)
- The smoke test checked end-to-end data flow but not symbol_id
  round-trip correctness — it accepted "UNRECOGNIZED trade" as
  "trade data flowing"
- There is no shared header file between Python and C++

The bugs were only visible when:
1. A consumer cared about specific field values (symbol_id for
   orderbook auto-selection)
2. Someone compared the Python `struct.pack` format string to the
   C++ struct field order and noticed the size mismatch

## Prevention: generate a shared constants header

The right fix is to generate one source of truth that both sides import.

### Option A: C++ header as truth, Python reads it

```python
# btquant_shm_layout.py (generated)
# AUTOGENERATED from include/hotspine_data_bridge.hpp — do not edit
HEADER_SIZE = 4096
TRADE_SIZE = 40
OB_SIZE = 6464  # alignas(64) on HotOrderbookSnapshot
OB_HEADER = 24
OB_DATA = 6400  # 200 levels * 16 bytes * 2 sides
OB_PAD = 40     # 6464 - 24 - 6400
TRADE_CAP = 50000
OB_CAP = 2000
```

Add a CMake target that runs a script to generate this from the C++
header:
```cmake
add_custom_target(generate_shm_layout
    COMMAND python3 ${CMAKE_SOURCE_DIR}/scripts/gen_shm_layout.py
            ${CMAKE_SOURCE_DIR}/include/hotspine_data_bridge.hpp
            ${CMAKE_BINARY_DIR}/btquant_shm_layout.py
    DEPENDS ${CMAKE_SOURCE_DIR}/include/hotspine_data_bridge.hpp
)
```

### Option B: Python header as truth, C++ reads it

Less common but possible — generate the C++ struct from a Python
schema definition using a tool like `pybind11` or a custom generator.

### Option C: Manual sync with a verification step

If you can't generate one from the other, add a CI check that
verifies both sides agree:
```bash
python3 -c "import struct; print(struct.calcsize('<QQIBB2s'))"  # should be 24
python3 -c "import subprocess; print(subprocess.check_output(['pahole', 'HotOrderbookSnapshot']))"  # extract sizes
```

## Detection script for the current state

```python
import mmap, struct

SHM = "/dev/shm/btquant"
HDR = 4096
TRADE_SZ = 40
OB_SZ_PYTHON = 6464  # what mock_data_producer.py uses

with open(SHM, "rb") as f:
    with mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_READ) as shm:
        ob_base = HDR + 50000 * TRADE_SZ
        # Read symbol_id at offset 16 in each orderbook
        for i in range(5):
            sid = struct.unpack_from('<I', shm, ob_base + i * OB_SZ_PYTHON + 16)[0]
            print(f"  slot {i}: symbol_id={sid}")
```

If all slots show valid IDs (1-20 for the 20 test symbols), the
strides match. If you see garbage values, the strides don't match.
