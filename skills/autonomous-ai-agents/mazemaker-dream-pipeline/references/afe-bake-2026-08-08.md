# AFE Corpus Bake 2026-08-08 — DeepSeek one-off over the whole corpus

Context: the A→B→C chain never ran in production. Root causes found & fixed on
2026-08-07/08 (commits in mazemaker-pro):

1. **0-byte SQLite shell** (e9e9670): `~/.mazemaker/data/memory.db` = 0 bytes
   since the PG migration; `_phase_afe` read `stream_long_memories_for_afe`
   from SQLiteStore → "AFE: 0 sources" every cycle → B=0 for months, C never.
   Fix: PG-first when `_postgres_store` armed. Verified with a fake-Memory
   harness (sqlite store WITHOUT the streamer, pg store WITH it → phase must
   NOT report "missing streamer").
2. **Cascade hid Stage C** (3539c0c): `extract_atomic_facts` ran C only if
   A+B yielded nothing. `enable_llm_always=True` appends C after A/B.
   Verified with mock LLM server: always→A+C (call made), fallback with
   A-facts→no C call, fallback with empty A/B→C call (old path intact).
   Note: `_NUMERIC_TOKEN_RE` in afe.py matches only $42 / 42% / dates /
   phones — NOT bare numbers ("Alter: 42" is rejected by `_looks_atomic`).
   Use "$42"-style bullets to force A-stage facts in tests.
3. **Monster done-set** (dbcd3a6): `meta.afe_processed_ids` carried tens of
   thousands of ids (462 kB text!) from months of broken runs → bake saw
   "0 sources" instantly. `MAZEMAKER_AFE_DONE_KEY` gives the bake its own
   processed-set.
4. **Cloud transport** (b0184d2): `MAZEMAKER_AFE_API_KEY` → Bearer header,
   repeat_penalty dropped for cloud (OpenAI-compatible endpoints 400 on the
   llama.cpp-native sampler), frequency/presence kept.

## Working bake recipe (bake-afe-deepseek.sh pattern)
podman run --rm --pod mazemaker --user 0 --device nvidia.com/gpu=all \
  -v ~/.mazemaker/{data,sockets,compute.toml,db.toml,license.jwt,jwt.v1.pub.ed25519}:... \
  --env-file ~/.mazemaker/db.env \
  --secret mazemaker_pg_password,type=env,target=MM_POSTGRES_PASSWORD \
  --env EMBED_BACKEND=http --env EMBED_CLIENT_ONLY=1 \
  --env MM_EMBEDDING_WORKER_URL=http://localhost:8766 \
  --env MM_RECALL_GPU_STRICT=1 --env MM_ALLOW_CPU_RECALL=1 \
  --env MAZEMAKER_AFE_LLM_FALLBACK=1 --env MAZEMAKER_AFE_LLM_ALWAYS=1 \
  --env MAZEMAKER_AFE_LLM_URL=https://api.deepseek.com/v1/chat/completions \
  --env MAZEMAKER_AFE_API_KEY="$KEY" --env MAZEMAKER_AFE_MODEL=deepseek-v4-flash \
  --env MAZEMAKER_AFE_LLM_REASONING=0 --env MAZEMAKER_AFE_LLM_TEMP=0.0 \
  --env MAZEMAKER_AFE_LLM_TRUNCATE=48000 --env MAZEMAKER_AFE_DONE_KEY=afe_processed_ids_bake \
  --env MAZEMAKER_AFE_SKIP_CHUNKS=1 --env MAZEMAKER_AFE_MAX_PER_CYCLE=3000 \
  --env MAZEMAKER_AFE_WORKER_ID=$i --env MAZEMAKER_AFE_N_WORKERS=4 \
  --env PYTHONPATH=/app/core:/app/shared:/app \
  localhost/mazemaker-v2-mcp:gpu \
  python3 -c "import sys; sys.path.insert(0,'/app'); sys.argv=['dream_worker','--phase','afe','--once','--log-level','INFO']; from dream_worker import main; main()"
Loop per worker until the log says "AFE: 0 sources". Key lives in
~/.mazemaker/afe-deepseek.env (0600). After the bake: llama takes over again
(the afe-window service is untouched local DeepHermes).

## Operator principles (from this session)
- NO invented facts: reasoning off, temp 0.0, prompt's negative rules
  ("output [] if none", never invent) stay in force.
- Dream cycles must NEVER process the whole corpus — batch one-offs only.
- "parallel == bloat": each process with its own tensor/CUDA context is
  bloat; one canonical tensor; HTTP embedding for everything else.
- Benchmark sessions/terminal logs (e.g. benchwrap, "[neural-memory:RO]",
  "DROPPED") pollute the live corpus via the session ingest — ~500 chunks of
  LongMemEval run logs found in 215k memories (id 94880 is one). No ingest
  filter exists yet; candidates for cleanup + a selftest pattern.
