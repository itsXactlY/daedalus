## Deploy model (read this first — it explains most "why is prod different from git" confusion)
- `python/` is source of truth; `hermes-plugin/` is a mirror; the podman containers (`~/.config/containers/systemd/mazemaker-*.container`) run **their own deployed copy** which can lag the git tree by hours. Journal timestamps vs. container-file mtimes tell you which code/env was live during a run.
- Engine policy now comes from `compute.toml` (`/root/.mazemaker/compute.toml`, rendered by license-client; keys set on mazemaker.dev). Old env gates (`MM_*_ENABLED`, `MAZEMAKER_SYNTHESIS_*`) are marked [LEGACY] and warn when set. **Dead-key check:** compute.toml contains keys nothing reads (verified 2026-08-07: `synthesis_model`, `synthesis_min_conf`, `synthesis_min_evidence`, `synthesis_timeout_s`, `[afe].model` — engine reads env only). Grep `python/*.py` for each key before trusting it.
- Worker env (dream-worker.container): `EMBED_BACKEND=http`, `OLLAMA_HOST=http://host.containers.internal:11434`, `MAZEMAKER_SYNTHESIS_MODEL=qwen2.5:3b`. mcp.container: `EMBED_CLIENT_ONLY=1`, `EMBED_BACKEND=` (empty), still had `MAZEMAKER_SYNTHESIS_WINDOW_S=86400` (as of 2026-08-07).

## 7-phase cycle (order in `_run_dream_cycle`)
NREM → SUPERSEDES → REM → Insight → AFE → SYNTHESIS → DAE. **Failure semantics: no phase can abort the cycle.** Every phase catches its own exceptions, writes partial stats, cycle continues. Only `cancel_check` (SIGTERM) stops between phases. `_run_dream_cycle`'s outer except catches only outside-phase errors. A phase that "looks fine but does nothing" is the norm to hunt for.

Key symbols (line numbers drift — search by name): `_phase_nrem`, `_phase_supersedes`, `_phase_rem`, `_phase_insights`, `_write_derived_cluster_memory`, `_prune_old_derived_clusters`, `_phase_afe`, `_phase_synthesis`, `_phase_dae`, `synthesis.synthesize_cluster`, `compute_config.get/flag`, `_derived_cluster_ttl_s`.

19. **Superseded versions stayed in the paging list — FIXED 35ad99e**: supersedes traversal demoted the superseded row by −0.5 but KEPT it in the result set — with few hits it still landed in the top-k (operator finding 2026-08-08: Judge-54/52 paging showed stale versions; supersedes only applied at the curated lookup, not in the ranking). 20. **Env-knob-name mismatch + one-sided gates — FIXED 5396678 + a512c36 (the "überschriebene Fixes" class, measured 2026-08-08 on the real 215k)**: two silent gate failures made the operator's OFF-knobs inert:
    - **DAE env-name mismatch (5396678)**: the quadlet sets `MAZEMAKER_DAE_ENABLED=0`, but `_phase_dae` read only the legacy `MM_DAE_ENABLED` (empty → "1") — the two names never met, so the full-corpus DAE compute (215,651 rows written) kept running, adding ~450 s to the cycle (measured: full cycle 525.9 s with DAE running vs 72.3 s with it skipped).     - **ColBERT read-path gate (a512c36)**: `MM_COLBERT_ENABLED=0` gated only token WRITES (`_colbert_write_enabled`); the READ channel weight came from retrieval-mode presets (0.5 for advanced/hybrid, 1.2 skynet) and the compute.toml overlay (1.5) — so embed_colbert HTTP calls kept firing every ~1 s during the cycle despite env=0 (measured 05:25). Side effect (intended): with NO env the channel is now OFF by default (was: mode preset), only explicit `MM_COLBERT_ENABLED=1` activates it. Verified matrix: env=0 + advanced/skynet/overlay-1.5 → 0.0; env=1 + advanced → 0.5; no env → 0.0. **Lesson: a feature gate that only guards one path (writes) while another path (channel weights / reads) is driven by a different config source is two separate switches for one feature — the env must be the final authority on BOTH.**

When the operator says "we used to have ~38s dream cycles, now it's minutes/hours" — do NOT assume the fast architecture was regressed. The docs/readme-rewrite branch (`git show docs/readme-rewrite:README.md`) documents the perfect era ("~38s on a 193k/~1M-edge corpus: NREM ~16s + REM ~12s + Insight ~2s"). Verified 2026-08-08: **ALL 6 core points are still PRESENT in master** — ① `think_ids()` fast path (no dict resolution, mazemaker.py:653 / memory_client.py:4506 / dream_engine.py:1737), ② PPR sparse mat-vec on CUDA adjacency cached across cycles (`_invalidate_gpu_ppr_adjacency`, dream_engine.py:1712/1717), ③ REM `recall_batch` = one embed_batch + one matmul + one topk (gpu_recall.py:493 / dream_engine.py:2247), ④ REM bridge writes in ONE transaction (~6000→1, dream_engine.py:2259/2294), ⑤ `add_one()` appends immediately (gpu_recall.py:355), ⑥ "no silent fallback" (MM_RECALL_GPU_STRICT). **If all 6 are present, the slowdown is DATA VOLUME + write-path latency, not missing code.** Time-levers that actually move it (the 38s era ran on SQLite; PG was added 30.04, AFTER the 38s doc of 28.04 — PG per-statement overhead + row locks made the per-edge NREM writes slower):

## Audit methodology (proven sequence)
1. **Map the cycle:** grep `^    def ` in dream_engine.py; read `_run_dream_cycle` + each `_phase_*` fully; note every `except` with what it swallows (dream_engine.py had 54).
2. **Git archaeology for "when did X break":** `git log --follow --format='%h %ad %s' --date=short -- <file>` for milestones; `git log -S "<string>" -- <file>` to find the commit that introduced a constant/window/gate (e.g. `-S "keep_seconds=5 * 60"`, `-S "MAZEMAKER_SYNTHESIS_WINDOW_S"`); `git blame -L` for defaults. Compare introduction commit against the code it was added NEXT TO (mismatches born with a feature, e.g. synthesis window 3600 vs pre-existing 5-min TTL prune).
3. **Production forensics:** `journalctl --user -u mazemaker-dream-worker` (grep `SYNTHESIS:|Insight cycle:|AFE:`); note container vs host time offset (was 2h); correlate PID/restart times with container-file mtimes (`stat`) to know which env/code was live; the `_model_present` fast-path shows up as a suspiciously fast run (<10s) with 0 proposals.
4. **Config dead-key check:** for each compute.toml key, `grep -rlE "\"key\"|'key'" python/*.py` — compute_config.py alone does NOT mean it is read; only `compute_config.get/flag` call sites in dream_engine/afe count.
5. **RAM:** when pod is down, reconstruct from commit messages (`git show <hash>`) + code attrs; measured numbers live in commit bodies (e.g. 94cdc80, d8fa3d6).
6. **"Did phase X ever succeed?":** grep journalctl + `logs/` + `benchmarks/logs/` for the phase's result tokens with `> 0`; distinguish bench-harness direct calls (synthesize_cluster run on host) from the engine phase — the bench succeeding does NOT mean the engine phase ran.
7. **PG error forensics (see `references/pg-deadlock-2026-08-08.md`):** `journalctl --user -u mazemaker-pgvector --since '6 hours ago' | grep -oE 'ERROR:  [a-z ]+' | sort | uniq -c` for the distribution; resolve relation OIDs via `SELECT oid, relname FROM pg_class WHERE oid IN (...)`; the full deadlock blocks (with the actual statements) appear in the log when `log_min_error_statement` is on — they show the DDL (e.g. `CREATE TABLE IF NOT EXISTS dream_sessions`) that took the AccessExclusiveLock. Check `pg_stat_database` (deadlocks, xact_rollback) and `pg_stat_user_tables` (n_dead_tup vs n_live_tup, last_autovacuum): dead ratio < 20 % is below the autovacuum threshold (normal, not a failure); after big retention deletes the table SIZE does not shrink — that is VACUUM FULL territory, only in a maintenance window (AccessExclusiveLock, never while bake/worker run). **n_live_tup/n_dead_tup are ESTIMATES — after heavy deletes they can be off by orders of magnitude** (measured 2026-08-08: connection_history showed "5.742 live / 0 dead" while `SELECT count(*)` returned 18,259,451 — the real value; the VACUUM FULL had compacted but not re-estimated). Always verify with count(*) before acting on pg_stat numbers; a table that "looks tiny" may be the biggest bloat source.
8. **Exhaustive every-function audit (when "ALLES testen" is demanded):** suites alone leave most production paths untested — settrace coverage measured 416 defs, only 182 executed by all three suites (56 % gap). The BIG gap: postgres_store + dream_postgres_store (103 functions) had ZERO suite coverage — the production backend was entirely untested. Method: (a) AST-inventory every def/class/method in the core modules; (b) run all suites IN-PROCESS under `sys.settrace` (collect `call` events, return a nested trace fn that stops line-tracing per function for speed) via `runpy.run_path(suite, run_name='__main__')`; (c) diff defined vs executed per module; (d) write targeted behaviour tests for every gap. PG behaviour tests CANNOT run from the host (the pod exposes no host ports) — run them in a throwaway container on the SAME pod (`podman run --rm --pod <pgvector's pod> --secret mazemaker_pg_password,type=env,target=MM_POSTGRES_PASSWORD -v <script>:/audit.py:ro -v mazemaker-pro/python:/app/core:ro -e PYTHONPATH=/app/core localhost/mazemaker-v2-mcp:gpu python3 /audit.py`) against a THROWAWAY DB (`CREATE DATABASE mazemaker_test`) — never the production DB. Results 2026-08-08: 75/75 PG-store functions + 65 further gaps, 0 findings. **Most "findings" in such an audit are the TEST's wrong guesses about signatures — read the actual `def` signature before writing the call, and use two EXISTING ids for FK-constrained edge writes (a `mid+1` target violates the FK).**

## AFE corpus bake (one-off A→B→C with a cloud LLM) — see references/afe-bake-2026-08-08.md
Operator principle: **"KEINEN erfundenen Blödsinn"** — extraction bakes must be deterministic (reasoning OFF, temperature 0.0), and **dream cycles must NEVER walk the full corpus** (batch-style one-offs only; the cadence is sample-based by design). "parallel == bloat": every process carrying its own tensor/CUDA context is bloat — one canonical tensor, HTTP embedding for the rest.
- Deterministic Stage C transport (afe.py b0184d2): `MAZEMAKER_AFE_API_KEY` switches the OpenAI-compatible HTTP path to cloud mode — Bearer header, and the llama.cpp-native `repeat_penalty` is DROPPED (cloud endpoints 400 on it), keeping frequency/presence penalties. Without the key, local llama-server/ollama keep the native field.
- Bake env matrix (proven): `MAZEMAKER_AFE_LLM_FALLBACK=1` + `MAZEMAKER_AFE_LLM_ALWAYS=1` (C additionally to A/B) + `MAZEMAKER_AFE_LLM_REASONING=0` (no deep-think; `_reasoning_mode` auto-detects only "hermes" in the name) + `MAZEMAKER_AFE_LLM_TEMP=0.0` + `MAZEMAKER_AFE_LLM_TRUNCATE=48000` (the plain-path default 3000 chars guts session blocks) + `MAZEMAKER_AFE_DONE_KEY=afe_processed_ids_bake` (own idempotency set) + `MAZEMAKER_AFE_SKIP_CHUNKS=1` + `MM_ALLOW_CPU_RECALL=1` + `MAZEMAKER_AFE_CALL_WORKERS=8` (threaded bulk extraction, 741384a: Stage C is HTTP I/O, a thread pool multiplies throughput at zero VRAM/cuda cost — "bulk, not snippet"; default 1 keeps normal cycles sequential). **Operator directive "parallel == bloat": ONE worker, NO `--device nvidia.com/gpu`** — every bake container that armed the 0.88 GB recall tensor multiplied VRAM (4 workers ≈ +3.5 GB) for work that needs no GPU (fact embedding goes over the HTTP worker, which stays on GPU). Without the device the arm falls to CPU (host RAM only) and DeepSeek calls run unchanged.

## Pitfalls
- Line numbers in any earlier audit brief will have drifted (e.g. 3592→3754 lines). Re-locate by symbol.
- `dream_engine.py`'s env defaults override module defaults in synthesis.py — always check the CALLER's default, not just the callee's.
- The 4/4-runs forensics: journal kept only 4 `SYNTHESIS:` lines ever — absence of a summary line on later runs means the phase is now *skipped* (compute.toml `stage_s_enabled=false`), not succeeding.
- `stage_s_enabled=false` in compute.toml currently disables synthesis entirely — flip on mazemaker.dev, not by env.
- Deployed container code can be older than the git tree; do not assume the tree you read is what ran.
- **Free/Pro-Grenze (operator rule, corrected 2026-08-08): SQLite ist FREE VERSION ONLY — sie bekommt NUR die Tabellen, die sie braucht, aber NIEMALS die Funktionen eines Pro-Stacks.** A missing Pro table in the SQLite schema (e.g. `memory_dae_embeddings` absent) is the INTENDED no-leak guard, NOT a bug — do not "fix" it by adding the table to the SQLite schema (I did, reverted 419c882→35d7d4c). Pro paths are `has_feature()`-gated; a bare call crashing on a fresh SQLite DB is the guard working. The PG store keeps its `ensure_dae_schema`.
- **Test-suite honesty (repaired 2026-08-08):** env-dependent tests must SKIP, not fail red — sentence_transformers without torch (the backend raises at instantiation, not import: put the constructor call INSIDE the try), C++ bridge without build/ (raises at `MazemakerCpp()` instantiation, not at import — the constructor also belongs in the try), hermes plugin tests without an installed plugin (check the plugin dir first), auto-connections without a semantic backend. The `@_testcase` wrapper swallows SkipTest and logs `SKIP` — assert on the RUN OUTPUT, not on a direct call expecting a raise.
- **Shadowed test functions:** two `def test_31()` in one file — the SECOND definition silently wins and the first test never runs. After adding tests, grep for duplicate function names; a missing regression test in the output is a shadowing symptom.
- **set -euo pipefail kills pipelines silently:** an `xargs -I{} sh -c '... printf "%s\0"'` filter produced a CONSTANT hash (dash's printf ignores \0, the while-loop's final read exits 1 → pipefail aborts the rest). Symptom: engine-sha never changed despite content edits. Fix: plain `grep -vE` + `xargs -d '\n'`; and verify the script's default source is the PRO repo (`$HOME/projects/mazemaker-pro/python`), not the free repo.
- MCP-Schema vs Engine-Signatur: recall_advanced's schema advertised `mode` but `Memory.recall` had no such kwarg → TypeError on EVERY call, wrapped as "Internal tool execution error" (2165390). When a tool layer (tools.py / mcp_schemas.py) maps to an engine method via kwargs (`_ENGINE_TOOL_TO_METHOD`), diff the schema's advertised parameters against the real method signature — a mismatch is a guaranteed runtime TypeError, invisible in unit tests that call the method directly.
- Cluster-label drift defeats id-based dedup signatures: Louvain (and most community detectors) re-labels communities every run — a membership-stable community can get a different id, and a (count, top-3-ids) dedup signature then re-fires almost every cycle (measured: 30k bridge insights/cycle despite a working cache). When the underlying clustering re-labels, sign dedup caches on size/count aggregates (e.g. top-3 community SIZES) — robust against renumbering, still sensitive to real structural change. Verify the signature's stability with the drift case (same sizes, different labels → must be EQUAL) before trusting it on the long-running worker.
