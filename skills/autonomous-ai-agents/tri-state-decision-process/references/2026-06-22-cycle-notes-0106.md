### Recall API recency-bias noise — filter and analyze technique

This cycle surfaced a NEW non-obvious pattern in `mazemaker_recall` that future cycles need to know about.

**Problem:** When using `mazemaker_recall(query=<topic>, limit=10)` to score a candidate's graph connectedness, the TOP result is often a memory created in the last few hours that has high cross-query similarity. In this cycle, memory 825792 (discovery:pulse-wurm-20260622_freshdir-rarepeds01, created 2026-06-22 00:30Z) appeared as the top result for EVERY topic-recall query, regardless of the actual topic — including queries about CVE nginx, GODMODE injection, gascity, satellite orbit debris, etc.

**Root cause:** The recall engine uses hybrid semantic + recency ranking. A very recent memory (created within the last hour) gets a recency boost that overrides the semantic-similarity signal for any other query. The 825792 discovery has vague "rare pediatric disease" content that triggers some semantic overlap with many topics (clinical, AI, deployment, infrastructure, health, etc.), and the recency boost amplifies the relevance score above genuinely-on-topic older memories.

**Workaround applied this cycle:** Filter out the recall-bias-noise result (identified by its high similarity across unrelated queries, or by being the most recent memory in the corpus) before counting fact:*/decision:* labels in the top 10. The actual topic-relevant results are usually at positions 2-10.

**Concrete technique:**
1. Run `mazemaker_recall(query=<candidate_topic>, limit=10)` and capture the structured `results` field.
2. Identify the most-recently-created memory in the results (highest `id` is a strong proxy for recency on a continuously-incrementing primary key).
3. If the most-recently-created memory appears in EVERY recall query's top-1 across this cycle (or has very low topical relevance to the query), exclude it from the top-10 count.
4. Count fact:*/decision:* labels among the REMAINING 9 results for connectedness scoring.

**Why this matters for connectedness scoring:** The connectedness score is `fact_or_decision_count / 10`. If the bias-noise result is a `discovery:` label (like 825792 in this cycle), it does NOT count toward fact/decision ratio, so the raw count is unchanged. But if the bias-noise result happens to be a `decision:` or `fact:` label (which is also possible), the count is inflated. The filter is most important when the bias-noise result is a decision or fact memory that the connectedness formula would over-count.

**Worth patching canonical-workflow.md as a Step 4 caveat:** "When scoring graph connectedness, watch for recall API recency-bias noise — a memory created in the last few hours may appear as the top result for unrelated queries due to recency-boost overriding semantic similarity. If the same memory appears in multiple unrelated topic-recall queries, exclude it from the connectedness count."
