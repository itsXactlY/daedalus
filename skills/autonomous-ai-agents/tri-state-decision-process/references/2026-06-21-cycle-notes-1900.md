## Discovery-pool enumeration — browse limit tradeoffs

This cycle used `mazemaker_browse(label_prefix="discovery:", limit=50)` and got exactly 50 results (162 KB persisted to file). The canonical-workflow.md says limit=100. Tradeoff observed:

- **limit=50**: ~162 KB result, manageable inline preview, 50 candidates (probably truncated from a larger pool). All candidates within last 24h.
- **limit=100**: would have returned potentially 2x the data; same parsing gauntlet but bigger persisted file.

For the 19:00 cycle, the 50-result browse was sufficient — the pool was thin (most fresh discoveries already covered in the dense 14:30 / 16:33 / 16:49 / 17:16 cycle stacks) and the top-36 candidates were clearly enumerable from 50. **Decision: stick with limit=50 in saturation-dense periods; bump to limit=100 only when the pool is genuinely under-saturated.**

This is a saturation-aware limit choice that the runbook doesn't currently encode. Worth a one-line addition to canonical-workflow.md §Step 1.

## Connectedness-as-generic-fallback — score formula limitation

For niche topics with no specific graph nodes, `mazemaker_recall(topic, limit=10)` returns the broader corpus's decisions as fallback. Connectedness count may be high (e.g. 9/10 = 0.9 for 825636 AI SRE tools), but topical relevance of the matches is LOW — the matches are decisions about gaming, Anthropic, NATO, etc., not about AI SRE tools.

**Score formula behavior:**
```
connectedness = count(fact:*/decision:* in top-10 topic-recall) / 10
```
This counts ANY decision:* label, not topic-relevant decisions. A niche-topic discovery with no specific nodes gets high connectedness (via generic-fallback) when it should arguably get lower connectedness (since none of the matches are topically related).

**Workaround used this cycle:** when computing connectedness, qualitatively check whether the top-10 recall matches are TOPICALLY related to the discovery. If 7+/10 are generic-fallback (not topic-related), discount connectedness by ~50%. For 825636 AI SRE tools: 9/10 generic-fallback, so effective connectedness was ~0.45 (not 0.9), and the total score should have been ~1.74 (not ~2.19).

**Better workaround:** query recall with a more specific query (longer phrase, more domain anchors) to bias the recall toward topic-specific results. If even a specific query returns generic-fallback matches, that's a signal of low graph presence.

This is a refinement of the canonical scoring formula — added as a §"Connectedness quality" pitfall in canonical-workflow.md.
