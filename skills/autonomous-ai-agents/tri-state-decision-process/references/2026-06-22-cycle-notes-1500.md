## Pool-saturation diagnostic at cycle start (NEW pitfall — formalized here)

**Context:** the existing "Stacked-cycle dedup at high discovery rates" pitfall covers the 2h-window rank count, but at high-activity days (3+ ranks per cycle × 4-6 cycles per day × dense cross-cluster coverage), the 2h window misses already-covered discoveries that were decided in earlier today-cycles (3-12h old). The full-day decision graph must be scanned to compute pool-health at cycle start.

**Pool-health formula (NEW):**

```
pool-health = count(uncov_2h) + count(uncov_full_day) + count(fresh_direction) + count(underrepresented_domain)
```

Where:
- `uncov_2h` = discoveries NOT yet decided in the 2h dedup window
- `uncov_full_day` = discoveries NOT yet decided as primary in ANY today's decision
- `fresh_direction` = discoveries from fresh-direction picks (the discovery content explicitly says FRESH-DIRECTION / picked_domain=)
- `underrepresented_domain` = discoveries from domains with <3 prior decisions in last 7d

**Diagnostic recipe at cycle start:**

1. Fetch 24h discovery pool: `mazemaker_browse(label_prefix='discovery:', limit=50)`.
2. Fetch today's decision graph: `mazemaker_browse(label_prefix='decision:rank-<YYYYMMDD>-', limit=50)`.
3. For each decision in today's graph, fetch the content and regex-extract `Discovery Memory ID:\s*(\d+)` for primaries + `826\d{3}` for PAIR/Companion/Sibling references.
4. Compute the set of covered discovery IDs (primaries + any discovery with 3+ cross-references per the "Cross-referenced-but-standalone SKIP pattern" pitfall).
5. Apply the 2h dedup filter to the remaining pool.
6. Compute pool-health on the remainder.
7. **If pool-health < 3**: apply the pad-to-3 anti-pattern strictly (2/2 or [SILENT]).
8. **If pool-health = 3**: write 3 NICE_TO_KNOW on 3 orthogonal axes (the 3-NTK full output case).
9. **If pool-health ≥ 4**: write the 3-rank output, optionally 1 IMPORTANT + 2 NICE_TO_KNOW if any IMPORTANT candidate qualifies.

## Sub-finding detection via recall-content-grep (NEW technique)

**Context:** the existing "Earlier-cycle rank-of-companion dedup" pitfall covers the case where a discovery is a companion/sub-finding of a discovery ranked in an earlier cycle (3+ hours old). The 2h dedup window is necessary but not sufficient.

**Refinement (NEW):** the content-grep technique is more reliable than topic-recall alone for sub-finding detection. The candidate's discovery ID may NOT surface as a top result for the topic-recall (recall ranks by semantic similarity, not by ID), so the explicit ID-grep is required.

**Diagnostic recipe:**

1. For each candidate discovery, run `mazemaker_recall(query=<candidate_topic>, limit=10)`.
2. For each result, fetch the content via `mazemaker_get(memory_id=<result_id>)` and regex `\b<candidate_discovery_id>\b` to check for explicit mention.
3. If the candidate's discovery ID appears in 1+ prior decision's content (any section — header, WHY IT MATTERS, PAIR, CLUSTER CONTEXT, DEDUP NOTE), the candidate is a sub-finding → mark as NOISE.
4. If the candidate's discovery ID does NOT appear in any prior decision's content, the candidate is novel → proceed to scoring.

**Inverse signal (NEW — recall-sparse = high novelty, mirror of Recall API recency-bias noise):** when the topic-recall returns mostly UNRELATED decisions (none of the top-10 mention the candidate's discovery ID or its specific proper-nouns), the candidate has no graph presence → high novelty score. This is the INVERSE of the existing "Recall API recency-bias noise" pitfall (which is about recall returning TOO-MANY-RELATED results). The two cases are mirrors:

- **TOO-MANY-RELATED recall** (existing pitfall): recall returns mostly topically-related decisions → candidate is part of a dense cluster → LOW novelty, HIGH connectedness (but possibly inflated — discount per the "Connectedness-score inflation from tangentially-related decisions" pitfall).
- **TOO-FEW-RELATED recall** (NEW): recall returns mostly UNRELATED decisions → candidate has no graph presence → HIGH novelty, LOW connectedness (but genuine — do NOT inflate per the "Connectedness scoring for under-represented fresh-direction domains" pitfall).

**Diagnostic test:** look at the top-3 of the topic-recall. Are they about the same topic as the candidate? If yes → dense cluster (low novelty). If no (e.g., "Polymarket Anthropic" decision surfaces for a "DAC engineering" query) → no graph presence (high novelty).
