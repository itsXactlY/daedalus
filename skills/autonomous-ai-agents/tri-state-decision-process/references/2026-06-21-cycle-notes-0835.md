## Pool-Thinness with High Prior-Cycle Throughput (NEW)

This cycle ran ~20 min after a major 08:15 cycle that wrote 3 fresh decisions (825476, 825477, 825478), ~30 min after an 08:00 cycle that wrote 3 more (825472, 825473, 825474), and ~1h20m after a 07:15 cycle that wrote 3 more (825463, 825464, 825465). The 2h dedup window therefore blocked 9 discoveries from re-ranking. The 24h pool still had 30 discoveries, but only 4-5 were uncovered by ANY decision today, and only 1 was fresh (within 2h).

**Strategy (PATCH AS A STEP):** When the discovery pool is thin (most items already covered by prior cycles), apply the **freshest-first + standalone-elevate** rule:

1. **RANK #1 (always):** the FRESHEST discovery not yet covered, even if it's a low-priority research signal. This preserves the "top-3 are recent" cadence property and gives ACT something new to chew on.
2. **RANK #2 / RANK #3:** borderline-aged candidates (1-3h old) that have been REFERENCED in cluster context but not elevated to a standalone `decision:rank-*` decision. These are valid elevation candidates because they add a new angle without re-ranking the same content.
3. **Avoid:** re-deciding a discovery that was decided 2h+ ago, even if it would now score higher. The dedup window exists for a reason — re-ranking the same item burns ACT's budget on the same content.

**Concrete example (this cycle):**
- 825475 (gaming-crisis-iscram, 28 min old, FRESH, NICE_TO_KNOW) → RANK #1
- 825457 (0630 pulse-tick, 1h47m old, IMPORTANT, standalone-elevate) → RANK #2 (was a sub-finding of 825235/825208 cluster context, not its own decision)
- 825455 (startup-roundup, 2h26m old, NICE_TO_KNOW, standalone-elevate) → RANK #3 (was mentioned in 825463 as a sub-finding of the 0609 tick, not its own decision)

## Contradictory-Decision-as-Novelty Signal (NEW — high-value pattern)

When a recent decision (or bug memory) declares something RESOLVED and a new tick observation contradicts that resolution, the new tick is a high-novelty signal — the prior fix was partial, not complete. This is a stronger novelty trigger than the standard "1 − max_similarity" formula can capture.

**Pattern (PATCH AS A PITFALL):** Before scoring a discovery, scan the topic-recall top-10 for any `bug:*` or `decision:*` memory that claims RESOLVED status. If found, check whether the new discovery is consistent with that resolution. If the new discovery contradicts the RESOLVED claim, the discovery is a **partial-fix signal** — boost the novelty interpretation and elevate to a new rank.

**Concrete example (this cycle):**
- `bug:pulse-wurm-pm-locale-pollution-resolved-2026-06-20` (825208) declared the PM locale pollution bug RESOLVED with a regex filter dropping non-(en|es|pt-br) locale paths.
- 825457 (0630 pulse-tick) reports: "Polymarket noise is now the #1 anti-pattern in deep research: when a query touches a prediction market, ~20 locale variants... share the same parent URL cluster and inflate cluster scores to 10000+ vs. legitimate 6-7 score substantive items."
- The 825208 fix was about LOCALE variants; 825457 reports that the underlying CLUSTER problem (URL clones inheriting parent cluster's high final_score) is the residual anti-pattern even after the locale filter.
- Verdict: 825208 is PARTIALLY-RESOLVED, not RESOLVED. 825457's recipe ("DROP polymarket from sources OR post-filter the returned 20 by URL pattern") is the new actionable improvement.

**Why this matters:** The standard novelty formula (1 − max_similarity) gave 825457 a novelty of 0.40 (max sim 0.5962 to 825208). Without the contradiction check, 825457 might have looked like a cluster extension of 825208 and been deprioritized. With the contradiction check, 825457 elevated to IMPORTANT with a 0.10 priority boost.

## Connectedness Inflation for 0-Coverage Topics (NEW)

When a topic has 0 graph coverage (e.g., a fresh-direction domain that's never been explored), the topic-recall returns the CORPUS-WIDE decision base via semantic fallback. The rubric says "count how many of the top 10 results are fact:* or decision:* labels" — by the letter of the rule, all 9 corpus-wide decisions count. But semantically, the 9 are not connected to the topic.

**Pitfall (PATCH AS A NOTE):** For 0-coverage topics, the connectedness score as computed per the rubric is the FLOOR (0.9), not a meaningful signal. The decision prose should distinguish:
- **Real graph integration:** the topic has prior decisions/facts that specifically address the topic, contributing genuine context
- **Recall fallback:** the topic has 0 graph coverage; the recall returns whatever the engine finds semantically closest in the broader corpus, which is rarely the same domain

**Concrete example (this cycle):**
- 825475 (gaming-crisis-iscram) had 0 graph coverage — the gaming domain was the alphabetically-first under-covered bucket.
- Topic-recall for "serious gaming crisis bibliometric research paper ISCRAM" returned 9 decisions: 825086 tick-summary, 822479 inference-substrate, 824950 spacex-ai-cloud, 825405 anthropicapacity, 822429 fine-tuning, 825421 pi-hunter-ops, 822514 agentskillmalware, 822501 clawhub-security, 825349 climate-data-center-eia, 825052 pulse-lineage-protocol.
- None of these are gaming-related. They are the corpus's high-engagement decisions that the engine's semantic similarity finder returns for a generic "research" query.
- Connectedness by rubric: 0.9. Connectedness in reality: 0.
- Decision prose should note: "9 of 10 topic-recall results are decision:* — gaming is 0-coverage, so the topic-recall returns the corpus-wide decision base; [list]. The 0.9 connectedness is an artifact of topic-coverage gap, not real domain integration."

**When to use this caveat:** any time a discovery is in a low-coverage domain (gaming, music-art, infrastructure-systems-design, etc.) AND the topic-recall returns decisions that don't reference the topic. The caveat belongs in the SCORE BREAKDOWN section.

## Browse-with-Label-Prefix Dedup Pattern (refinement of existing 0800 technique)

The 0800 cycle already documented `mazemaker_browse(label_prefix="discovery:", limit=100)` for finding fresh discoveries. The 08:35 cycle refined this for DEDUP: `mazemaker_browse(label_prefix="decision:rank-YYYYMMDD-", limit=30)` returns today's decisions in reverse-chronological order, fast (~100KB JSON), with all the `Discovery Memory ID:` references extractable by regex.

**Efficient dedup pattern:**
```python
# Step 1: build decision-map
mazemaker_browse(label_prefix="decision:rank-20260621-", limit=30)
# Extract: {discovery_id: (decision_id, decision_created_at)}

# Step 2: for each discovery in 24h pool
#   if discovery_id in decision_map and (now - decision_created_at) < 2h:
#     skip (dedup window)
#   else:
#     eligible
```

This avoids the per-discovery recall-based dedup queries (slower) and produces a deterministic skip-set. Combined with the ranking-map construction pattern from `2026-06-21-cycle-notes.md`, the 08:35 cycle's dedup took ~30s vs the naive per-discovery approach's ~5min.
