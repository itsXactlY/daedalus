## Critical gotcha discovered: narrative-reference false positive

A naive `if str(tid) in content` check for whether a discovery is covered returns FALSE
POSITIVES when prior decisions narratively reference unranked discovery IDs in CYCLE
CONTEXT or PAIR sections. Worked example:

The dario-amodei decision (826460, 17:15) narratively states:
> "last decision cycles in window are 17:15Z (826455 AlphaFold-Nvidia-Eli Lilly IMPORTANT,
> 826457 Steam AI disclosure NICE_TO_KNOW, 826447 Dario Amodei NICE_TO_KNOW)"

A grep for "826455" or "826457" in 826460's content returns HITS, but 826455 and 826457
are NOT actually covered — they are raw `discovery:` labels (verified via
`mazemaker_get(memory_id=826455)` returning a `discovery:` label, not `decision:rank-*`).
The 826460 text is a forecast of what the 17:15 cycle WOULD HAVE ranked, not actual
coverage.

**The fix: content-extracted ID check MUST match the canonical `Discovery Memory ID:`
line, not bare numeric token presence.** The regex in `references/decide-tool-mechanics.md`
"Content-based dedup extraction" section is correct:

```python
import re
m = re.search(r'Discovery Memory IDs?:\s*(\d+(?:,\s*\d+)*)', content)
if m:
    ids = [int(x.strip()) for x in m.group(1).split(',') if x.strip().isdigit()]
```

The `Discovery Memory ID:` prefix is the load-bearing signal — it does NOT appear in
narrative/PAIR/CYCLE CONTEXT text. Bare `str(tid) in content` is unsafe at 30+ saturation
and WILL false-positive at 50+.

**Verification step for disputed candidates:** when dedup is ambiguous, run
`mazemaker_get(memory_id=tid)` to confirm the LABEL is `decision:rank-*` (covered) or
`discovery:*` (uncovered). One extra tool call per disputed candidate eliminates the
false-positive class entirely.
