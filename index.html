01 · the turn, dissected

One turn of the agent loop

The whole agent is one synchronous loop in run_agent.py (458 KB — the core file). Each iteration: build the turn, prefetch memory, call the model with live-tuned reasoning, broker the tool calls, spill what no longer fits, and re-steer effort for the next call.

The loop

run_agent.py:7510

while api_call_count < self.max_iterations and self.iteration_budget.remaining > 0:
    # 1. build the turn context
    # 2. memory prefetch (resume query + goals) fires before the loop body
    # 3. adjust_agent_reasoning(messages) — re-estimate effort from live state
    # 4. client.chat.completions.create(...) with tools
    # 5. broker tool calls (local tools + pony broker for external services)
    # 6. context compressor: prune + spill what aged out of the live window

Reasoning effort is steered mid-turn, not set at start

agent/task_intensity.py:333 — docstring, verbatim

"""On-the-fly reasoning adjustment for an agent object.

Auto mode is OFF unless agent.reasoning_auto is truthy. When auto is
on, re-estimates the task from *messages* and updates
agent.reasoning_config in place — the request builder reads it per
API call, so the very next call uses the new level.

Never downgrades below agent.reasoning_floor (default "low").
Respects explicit disable: {"enabled": False} stays disabled."

The task gauge reads the live message tail every iteration. A turn that starts as "rename a file" and becomes "debug a 4096-instance WebGL scene" changes level in-flight — the floor ("low") prevents the gauge from dropping below the operator's guarantee.

Iteration budget, not just max iterations

The loop stops when either the iteration cap or the iteration budget runs out. Long autonomous runs are rate-gated, not just count-gated — a stuck tool loop cannot burn a whole session's budget in a tight circle.

02 · context that outlives the window

Context spill

The window is bounded. The work is not. When tool results age out of the live window, the compressor does not delete them — it spills them to tmpfs, rewrites the context line to name the spill path, and lets the agent read it back verbatim later. Deletion was the old failure mode; the spill made it a pointer.

run_agent.py:462 — where spills live

@staticmethod
def _spill_root() -> str:
    """Where spilled tool output lives.

    DAEDALUS_SPILL_ROOT lets tests point somewhere disposable; without it
    a test that purges by age would delete a live session's spill and turn
    every handle in its context into a dangling path."""
    import tempfile
    override = os.environ.get("DAEDALUS_SPILL_ROOT")
    if override:
        return override
    base = "/dev/shm" if os.path.isdir("/dev/shm") else tempfile.gettempdir()
    return os.path.join(base, f"daedalus-ctx-{os.getuid()}")

The wedge, live — how it breaks, honestly

observed during this build, 2026-09-04 00:25–00:58

At 00:25 the pod answered 222,767 memories. By 00:58 the restarted wonderland instance reported 0 and recall returned empty. The mcp log said why:

semantic channel STRICT: reached the whole-corpus CPU brute-force fallback (PG-HNSW, GPU arm and HNSW all failed). Refusing the 7 GB / 75 s get_all() scan — fix the backend, or set MM_ALLOW_CPU_RECALL=1

The STRICT policy refuses to brute-force a 7 GB / 75 s full-corpus scan on CPU. A wedged channel fails closed into emptiness rather than returning garbage. Data integrity was verified the hard way — straight into the pgvector container:

psql → SELECT count(*) FROM memories;      → 222,767
psql → SELECT count(*) FROM connections;    → 1,503,408

Nothing was lost. The engine layer is swappable; the corpus is not. The repo even has a commit for this class of failure: 65e2529 — "Recover a wedged memory pod instead of only reporting it", and the plugin constants encode the lesson from 2026-08-30 (three silent ~2 h engine stalls): a READY verdict now expires after 60 s (_BRAIN_POSITIVE_TTL_S = 60.0) so a mid-session wedge is re-probed instead of trusted for the whole session.

04 · the router

ALICE — multi-angle recall

One query phrasing is not enough. The router runs up to three angles in parallel, fetches over-aggressively, fuses by reciprocal rank, and re-weights every hit by kind: what a human distilled vs. what was auto-saved. Fail-open, fail-honest

Routing is a degradation, never a gate: if the router wedges (3 consecutive failed pod calls → wedged verdict), the turn continues with zero memory injection rather than blocking. If the pod is down, the plugin goes cold — commit c36a804: "a dead pod goes cold instead of costing every call its timeout". The model still works; it just stops remembering, until the probe says READY again.

05 · skills, as a system

354 skills, none listed here on purpose

Skills are procedural memory — SKILL.md files with frontmatter, steps, pitfalls. The harness does not dump the catalogue into context (that killed prompt caching and bloated every turn). Instead: a one-line catalogue notice, deterministic matching, and the matched skills injected as a user message so the system-prompt prefix stays cache-stable.

agent/prompt_builder.py — the exact block every turn carries

## Skills (mandatory)
354 skills are installed. They are NOT listed here — this context stays free of
capabilities the current task does not need.
Before replying, check the latest user message for an [auto-routed skills ...]
block: the harness deterministically matched your task against all 354 and put
the candidates there. Prefer those. When none is offered, or none fits, call
skills_list(query='what you need it for') — it ranks the full set and returns
only the matches, so every skill is reachable without pulling the catalogue
into context. Load one with skill_view(name) and follow its instructions; a
loaded skill stays available for the rest of the session.
If a skill has issues, fix it with skill_manage(action='patch').

06 · autonomy

Systems that run without a babysitter

Autonomy is not a mode; it is the default. The harness ships cron, sub-agents, and self-healing data paths. What is live on this machine right now:

Cron jobs — from ~/.daedalus/cron/jobs.json

jobschedulestate

The dream cadence is owned by an external dream_worker.py process (dream_config confirms: "in-pod dream engine disabled; cadence is owned by the external dream_worker.py process") — that is how the 81,138,058 bridges and 62,149,687 insights accumulate without anyone touching the machine.

Sub-agents

delegate_task spawns isolated contexts (own conversation, terminal, toolset) — up to three in parallel, only the final summary returns. Reasoning-heavy subtasks (debug, review, parallel workstreams) never pollute the parent window. The parent keeps its cache prefix intact; the child does the hauling.
